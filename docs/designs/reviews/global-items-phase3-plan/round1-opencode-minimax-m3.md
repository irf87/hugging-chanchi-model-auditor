## What holds up

- **Coverage.** All five phase-3 deliverables of the design's *Adoption phases* row 3 (migration 006,
  `items scan`, `project items-dirs`, `items propose`, `agent-chanchi-item-builder`) map to a task
  with tests, and the phase signal ("`skill-chanchi-global-herdr` built from the consumer copies and
  accepted by a redundant audit") is reachable through Task 5. Nothing from phase 4+ is pulled in:
  `items inbox/decide`, `skill-chanchi-item-adoption` and the design's third proposal rule are
  explicitly out, and the third rule is deferred with a reason (it needs phase-4 decisions). The
  lessons #1-#7 stay pending, as the request asks.
- **The builder's source.** The Task 4 text parses with `agents_sync._parse` (name, description,
  scope `both`, profile `workspace-write`, `install: user`, `skills: []`), its 55 lines are far
  inside the 300-line budget of `tests/test_rules_budget.py`, it contains no home path and no
  reference-project name (`tests/test_privacy.py` clean), and it references only its own agent name.
  Its skill frontmatter shape (`name`, `description`, then `metadata:` with two-space-indented
  `version`/`status`) is exactly what `items.read_frontmatter` accepts, and its agent frontmatter
  shape is exactly what `agents_sync._parse` accepts. Its rules are harness-agnostic and correctly
  withhold publishing, mirroring, auditing and any chanchi record.
- **Fingerprints and the read-only guarantee.** D4's "no item text other than `description` reaches
  the database" matches the design's `project_items.description` column; the symlink skip, the
  non-UTF-8 skip, the depth limit and the "path reached from two roots is stored once" rule all
  hold against `items.content_hash` and the `UNIQUE (project_id, path)` constraint.
- **Independent uses.** D9's cluster/union-find model reproduces the design's rule (vendored copies
  count once, `min_uses` default 3, `vendored_share` default 0.5, `SYNC/config/promotion.toml`
  with exactly two keys) and the herdr case ends at `uses = 1` with `owner_promoted = 1` →
  `eligible`, exactly as the design's owner decision of 2026-11-21 requires.
- **Storage across runs.** D11's one-open-row-per-`(kind, name)` with the partial unique index, the
  `built`/`rejected` → `closed` path and the `not_found` path are consistent with D13's transitions
  and with the design's `item_proposals` table.
- **The read-only guarantee is testable as written.** The plan's snapshot test (every path, size and
  `mtime_ns` before and after) is the right instrument, and the gate's `git status --porcelain`
  comparison is the right end-to-end check.
- **Command and API names.** Every command the plan names exists with the flags the plan uses:
  `project register/list`, `items check/list/publish/retire/mirror`, `items proposal-status`'s
  `invalid_transition`, `sync status`, `agents sync [--check]`, `agents link --user [--check]`,
  `audit open --kind item --version`, `audit round --version`, `audit vote/dissent/close`,
  `session start --retry-reason`, `db migrate --template`, `db status`, `change close`. The
  scratch-home `agents link --user` command was run as written and lists the `install: user` agents
  for all three harnesses.
- **The gate's audit plumbing.** `chanchi audit open --kind item --ref … --version 0.1.0` records
  `subject_at = <version>@<content hash>` through `items.subject_at`, and a fix round at the same
  version re-hashes correctly — so the plan's "(the hash changes, the version does not)" is correct.
- **Layering.** The declared import edges are acyclic (`inventory` → `items`/`projects`/`sync`;
  `items` never imports `inventory`; the CLI passes the names across), and `tests/test_layers.py`
  imposes no further constraint on a new domain module.

Nothing here makes the plan unexecutable or contradicts the design in a way a fix cannot repair.
The seven major findings are all specification gaps that an executor would otherwise guess at —
three of them (S3-02, S3-03, S3-04) are places where the plan's own fixed artefacts (the gate's
pass criteria, the builder's byte-for-byte source, the plan's own test fixtures) do not determine
the answer, and one (S3-06) is a concrete `scripts/check` failure the plan's "only if" clause does
not cover.
